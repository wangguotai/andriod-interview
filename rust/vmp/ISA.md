# VMP-1 指令集与字节码规范（冻结版）

> 这份文档是「汇编器 / 虚拟机 / 三个受保护程序」三者的**唯一契约**。
> 任何一方要改语义，必须先改这里 —— 否则「对拍逐位一致」这条验收红线会以最贵的
> 方式失效：不是构建失败，而是算出一个看起来合理、但和目标值差一点的数。

## 0. 这份 ISA 为什么长这样

设计目标不是「做出一门好用的语言」，而是**让被保护的算子不再以机器码形态出现在 `.so` 里**。
由此推出三条硬约束，所有取舍都服从它们：

1. **可解释、可逐位对拍**：所有算术都必须在「解释执行」和「原生编译」两种情况下
   给出完全相同的位模式，否则加固就没法验证正确性。因此：
   - 只允许整数运算，**不引入浮点**（浮点的结合律不成立，跨实现会差末位）；
   - 乘法/加法**定义成回绕（wrapping）**，不做溢出检查 —— 与 Rust 的 `wrapping_*`
     和 C 的无符号语义一致，也和 JVM 的 `int`/`long` 溢出行为一致；
   - 除法有**两套**：`DIV/REM` 是无符号，`IDIV/IREM` 是有符号且**向零截断** ——
     这一点必须显式分开，因为 Rust 的 `/` 与 Kotlin 的 `/` 在负数上都是「向零截断」，
     而 C 的 `/` 是「向负无穷取整」。VM 只能选一种，我们选前者。
2. **反编译成本高于重写成本**：见第 3 节「操作数编码」，同一条指令有 1/2/3 字节的
   不同长度，且没有固定的指令边界可依赖。
3. **VM 本身要薄**：解释器是一个约 200 行的 `match`，读一遍就能确信它没有别的行为。
   加固对象的**算法**在字节码里，不在 VM 里 —— 这也是面试里最容易被问倒的地方，
   所以要在文档里写死。

## 1. 执行模型

- **栈机**：三个独立的栈 + 三个独立的地址指针，全部用 `u64` 格。
  - `stack`：主操作数栈，容量 4096 格。`top` 指向**下一个空闲格**。
  - `aux`：辅助数组，容量 4096 格。`top` 指向**下一个空闲格**（与 `stack` 同构，
    但不与主栈共享命名空间）。给直方图、行累加器这类「按索引存取的局部数组」用。
  - `mem`：**内存输入**（源图 / 目标图 / 工作缓冲的合并视图）。
    字节码只按**相对偏移**寻址，VM 把三段缓冲拼成一个逻辑地址空间。
    downscale 的 `dst` 是一个 32 位宽的**直写视图**（见 `mem_slot::DST`），
    写入即刻落到目标缓冲，不需要额外的「拷回」指令。
- **常量池**：`u64` 数组，由程序头部（**明文**，不加密）携带。
  为什么常量池不加密：它是「数据」不是「控制流」。把它加密会让 VM 每取一个常量都要
  解密，而它本身泄露的信息很少（本 Lab 的三个程序里，常量池主要是调色板与桶数）。
  这是一个**显式的、可被质疑的取舍**，不是疏漏 —— 真实加固器通常会把常量池也做
  分片混淆，代价是 VM 与构建链都复杂一档。
- **输入槽**：`inputs[i]` 是 VM 启动时由宿主（JNI 层）填入的 `u64` 数组。
  程序用 `PUSHN i` 读取。为什么走输入槽而不是常量池：尺寸、半径这些值在**每次调用**
  都可能不同，它们必须来自调用方，且不能出现在字节码里（否则等于把参数编进代码）。

## 2. 指令表

编码：`[opcode:u8][operand...]`。操作数类型见第 3 节。

| 值 | 助记符 | 操作数 | 语义（`S` 为 stack，`t` 为 top） |
|---|---|---|---|
| 0 | `HALT` | — | 正常结束，状态 `OK` |
| 1 | `PUSHI` | Leb | `S[t++] = imm` |
| 2 | `PUSHM` | Leb | `S[t++] = CONSTS[idx]` |
| 3 | `PUSHN` | Leb | `S[t++] = inputs[idx]` |
| 4 | `LOADB` | U8 dim | `a=S[--t]; S[t++]=mem_read(a, dim)`，**零扩展** |
| 5 | `LOADBS` | U8 dim | 同 `LOADB`，但**符号扩展**到 i64（供需要负数的色相差使用） |
| 6 | `LOADW` | U8 dim | 读 4 字节 **小端** 组成 u64（供 `mem_slot::DST` 直写视图读回） |
| 7 | `DSTOREB` | U8 dim | `a=S[--t]; v=S[--t]; mem_write(a, v as u8, dim)`，**地址在栈顶** |
| 8 | `DSTOREW` | U8 dim | 同 `DSTOREB`，写 4 字节小端（**地址在栈顶**） |
| 9 | `ADD` | — | `S[t-2] = S[t-2] +% S[t-1]; t--` |
| 10 | `SUB` | — | 回绕减法（负数以二补码表示） |
| 11 | `MUL` | — | 回绕乘法 |
| 12 | `DIV` | — | **无符号**除法；除数为 0 → 状态 `DIV_ZERO` 并停机 |
| 13 | `REM` | — | **无符号**取余；除数为 0 → `DIV_ZERO` 停机 |
| 14 | `IDIV` | — | **有符号**（i64 解释）除法，向零截断；除数为 0 → `DIV_ZERO` |
| 15 | `IREM` | — | 有符号取余，向零截断（即结果符号跟随被除数） |
| 16 | `AND` / 17 `OR` / 18 `XOR` | — | 按位，u64 |
| 19 | `SHL` | — | `S[t-2] << (S[t-1] & 63)`（移位量掩码 63，避免 UB 式未定义） |
| 20 | `USHR` | — | 逻辑右移，移位量掩码 63 |
| 21 | `ISHR` | — | 算术右移（i64），移位量掩码 63 |
| 22 | `LT` / 23 `GT` / 24 `LE` / 25 `GE` / 26 `EQ` / 27 `NE` | — | **有符号** i64 比较，结果 0/1 |
| 28 | `CMPLTU` / 29 `CMPGTU` | — | **无符号** u64 比较，结果 0/1 |
| 30 | `AUXRD` | U8 dim | `a=S[--t]; S[t++]=aux_read(a, dim)` |
| 31 | `AUXWR` | U8 dim | `a=S[--t]; v=S[--t]; aux_write(a, v, dim)`，**地址在栈顶**（先算值再压地址，写起来最自然） |
| 32 | `POP` | — | `t--` |
| 33 | `DUP` | — | `S[t]=S[t-1]; t++` |
| 34 | `SWAP` | — | 交换栈顶两格 |
| 35 | `OVER` | — | `S[t]=S[t-2]; t++`（复制次顶） |
| 36 | `JMP` | Leb rel | `ip = ip_next + rel`（`rel` 为**正数表示向后跳**，见第 3 节） |
| 37 | `JZ` | Leb rel | `S[--t] == 0` 时跳转 |
| 38 | `JNZ` | Leb rel | `S[--t] != 0` 时跳转 |
| 39 | `CALL` | Leb rel | 压入返回地址，跳转（`ret_stack` 容量 256） |
| 40 | `RET` | — | 弹出返回地址跳回 |
| 41 | `MINU` / 42 `MAXU` | — | 无符号 min/max |
| 43 | `MINI` / 44 `MAXI` | — | 有符号 min/max |
| 45 | `MODB` | U8 m | `S[t-1] = S[t-1] % m`（m==0 → `DIV_ZERO`） |
| 46 | `PACKRGBA` | — | `(r,g,b,a) → (r<<24)|(g<<16)|(b<<8)|a`，**恰好消费 4 格** |
| 47 | `MAD` | — | `(a,b,c) → a*b+c`（回绕），**恰好消费 3 格** |
| 48 | `AUXADDU` | — | `a=S[--t]; v=S[--t]; aux[a] += v`（回绕），**地址在栈顶**—— 直方图/累加器的融合指令 |
| 49 | `PUSHMD` | — | `idx=S[--t]; push CONSTS[idx]` —— 运行时变址取常量（表查找，如调色板） |

`PACKRGBA` / `MAD` / `AUXADDU` 是**复合指令**：把「图像处理里高频出现的 3~4 条操作」融合成一条。
这不是为了性能（VM 里它省下的只是几次 `match` 派发），而是为了**降低字节码的可读性与体积**：
一条 `PACKRGBA` 比四条独立的移位/或指令更难一眼看出「这是在打包像素」。

`AUXADDU` 值得单独说一句：`aux[a] += v` 是直方图与行累加器的**唯一**热模式
（dominant 的权重/亮度累加、downscale 的行累加器与计数器、blur 的通道和全都用它）。
用「读-算-写回」三条指令表达会同时带来两个麻烦：字节码体积翻倍，以及
「地址要压两次」这个易错点暴露给每一处手写序列 —— 而对拍测试只会告诉你「结果差一点」。

状态码（写入 `status`，`HALT` 或故障时停机）：

| 值 | 含义 |
|---|---|
| 0 `OK` | 正常停机 |
| -1 `BAD_OPCODE` | 未知操作码（字节码被篡改 / 版本不匹配） |
| -2 `BAD_OPERAND` | 操作数越界（常量池下标、输入槽下标、栈/aux 越界） |
| -3 `DIV_ZERO` | 除数为 0 |
| -4 `OOB` | 内存访问越界 |
| -5 `RET_UNDERFLOW` | `RET` 时返回栈为空 |
| -6 `BAD_HEADER` | 程序头校验失败（长度/校验和/MAGIC 不符） |
| -7 `STEP_LIMIT` | 超出指令步数上限（2 亿步）—— 字节码无法停机 |

**为什么 VM 必须有步数上限**：字节码就是被保护对象，也就是**可以被篡改的对象**。
一个把回边偏移改坏的补丁就能让解释器永远转下去 —— 在 Android 上表现为
「某个后台泳道线程 100% CPU」，不崩、不打日志，极难归因。加上限后最坏情况变成
「一次调用返回错误码」，可上报、可降级。这是**加固本身引入的新攻击面**，
必须由加固方案自己闭环。

## 3. 操作数编码：为什么没有「固定指令长度」可依赖

三种操作数编码，按助记符固定，但**长度可变**：

| 类型 | 编码 | 说明 |
|---|---|---|
| 无 | 0 字节 | 纯寄存器/栈操作（`ADD` 等） |
| `U8` | 1 字节 | 维度/槽位、`MODB` 的模数。**取值范围刻意留小**，因为它同时出现在字节码里，也是「变量维度」的载体 |
| `Leb` | **1~N 字节，无符号 LEB128** | 立即数、常量池下标、跳转相对偏移（跳转先 zigzag 再 LEB128） |

反编译难点正是由 `Leb` 提供的：
- 同一条 `JMP` 在小程序里是 2 字节，程序一长就变成 3 字节 —— **静态扫描无法按固定
  步长切分指令流**，必须完整实现 LEB128 解码 + 控制流分析才能得到一个**候选**边界。
- 更关键的是：加密后的字节码在 `.so` 里**没有明文操作码**，连「哪一段是指令」都不知道
  （见第 4 节）。LEB128 的作用是让「解密后」的分析也依然不便宜。

### 跳转偏移：zigzag + LEB128

跳转偏移的定义（必须记死，因为最容易差 1）：

```
rel = target_ip - ip_next        // ip_next 是「本条指令（含操作数）之后」的地址
ip  = ip_next + rel  ⇒  等价于直接跳到 target_ip
```

操作数里**不直接存 `rel`，而是存 `zigzag(rel)` 的 LEB128**：

```
zigzag(v)   = (v << 1) ^ (v >> 63)     // 高位的符号位「摊平」到最低位
unzigzag(z) = (z >> 1) ^ -(z & 1)
```

为什么必须 zigzag：`rel` 对循环回边（向后跳）是**负数**、对分支跳过（向前跳）是正数。
若直接 `rel as u64` 塞进 LEB128，负数的二补码是 64 位全 1 前缀，一条回边要占 10 字节；
zigzag 让 ±1 都落在 1 位数量级，正负都只需 1~2 字节。循环是热点，这个取舍是必要的。

**变长偏移的自指问题**：偏移编成几个字节取决于偏移值，而偏移值又取决于它前面所有
跳转操作数的编码长度 —— 这是个全局不动点。汇编器（`asm.rs` 的 `finish`）用迭代求解，
详见那里的注释。这同时也是给反编译者加的一道小摩擦。


## 4. 程序容器格式（加密前）

```
偏移 0   : magic        u32 LE = 0x56504D31  ("VPM1")
偏移 4   : isa_version  u32 LE = 1
偏移 8   : code_len     u32 LE             ; 字节码长度
偏移 12  : const_count  u32 LE             ; 常量池条目数
偏移 16  : checksum     u32 LE             ; 对「头部的 isa_version..const_count + 常量池 + 字节码」
                                           ;   做 FNV-1a 32 位
偏移 20  : consts       const_count × u32 LE
偏移 ... : code         code_len 字节
```

**加密只覆盖偏移 20 之后的 `consts + code`**（即头部 20 字节明文的 `isa_version`/`code_len`/
`const_count`/`checksum` 保留）；`magic` 也一样明文。

- 为什么留明文头：VM 启动时需要在**不解密**的前提下知道「要解密多少字节」「常量池多大」，
  否则连 `decrypt(blob, nonce, len)` 的 `len` 都无从谈起。
- 因此 `magic`/`isa_version`/`code_len`/`const_count`/`checksum` 是**可见的**：
  反编译者能知道「这里有一个 1.2KB 的虚拟机程序」，但看不到任何一条指令、也看不到
  常量池内容。这一点在文档里必须写明 —— 把「看不清内容」说成「完全看不见痕迹」是
  加固宣传里最常见的夸大。
- 字节码流式解密：VM **不**在启动时把整段揭密到堆上，而是按 256 字节页惰性解密并缓存
  （见 `vm.rs` 的 `CodePage`）。这样「一次性 dump 出完整字节码」需要主动 hook VM 的
  取指函数，而不是简单地 dump 一块内存。

## 5. 内建自检（`SELFTEST` 通道）

VM 持有一个**运行时**自检程序（`selftest.rs`，同样是 VM 字节码，但**不加密**，因为它不
承载算子算法，只是一组算术断言）。它一次性覆盖：有符号/无符号除法与取余的符号语义、
回绕、移位、有符号/无符号比较、LEB128 边界值、跳转方向。

为什么必须有它：VM 的语义是**我们自定义的**，没有任何现成的编译器/测试套件能验证它。
如果 VM 的 `IREM` 写成了「向负无穷截断」，那么所有把负数喂给 `IREM` 的算子都会静默算错。
自检的价值不在于「发现 VM 有 bug」，而在于**把「VM 与规范一致」变成一条可随时在
设备上重放的证据** —— 面试时可以直接把它跑给人看。

## 6. 版本与扩展

`ISA_VERSION` 参与头校验：VM 拒绝执行版本不匹配的程序。加指令时**不要**复用旧操作码，
只追加（`HALT=0` 起编号已固定）。当前占用 0..47。
