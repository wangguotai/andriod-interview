# 三方 SDK 线程滥用与治理

> 场景：App 接入大量三方 SDK，各 SDK 各自 `new Thread` / 各自建线程池，导致线程数量失控。
> 难点：**你改不了三方 SDK 的源码**。所以治理手段必须按「能否改源码」分层。

---

## 一、危害（四个层面）

### 1. 内存与资源层面

每个 Java 线程在创建时会 mmap 一段栈空间，Android 上**主线程默认 8MB，子线程 <1MB**（bionic 的 `FixStackSize`）。

⚠️ **关键校正：这 1MB 是「虚拟地址空间」的 reserve，不是物理内存。**
只有栈真正被写入时才落物理页、才计入 PSS。所以：

- 真正先被耗尽的是**进程的虚拟地址空间**
- 32 位进程逻辑地址 4GB、用户态 <3GB → 几百个线程就能把地址空间榨干
- 崩溃形态是 `pthread_create (1040KB stack) failed: OutOfMemoryError`

**这类 OOM 最难查的点**：抛出时 Java 堆充裕、设备物理内存也充裕，堆内存分析完全看不出问题。

- 64 位地址空间大，同样线程数通常不会 OOM，但 PSS 随栈占用增长，且**系统级线程数上限依然存在**

### 2. CPU 与性能层面

操作系统调度器需要做上下文切换。

⚠️ **两处校正：**

- 单次上下文切换在 **µs 量级**，说「大量 CPU 时间消耗在保存/恢复寄存器」是夸大了。
  真正的代价是 **cache / TLB 失效**——切到新线程后 L1/L2 工作集全冷，这个开销远大于寄存器保存。
- **不能一概而论「线程多 = 卡」**：
  - IO 密集型任务：线程多一些反而有益（等待 IO 时不占 CPU）
  - CPU 密集型任务：线程数超过核数才是纯损耗

### 3. 稳定性与功耗层面

- 后台线程不受控常驻 → App 在后台仍持续唤醒 CPU → 耗电飙升
- 可能被系统判定为**后台滥用**而杀掉进程

### 4. 架构层面

线程散落在各 SDK 里，导致：

- 无法统一监控
- 无法统一取消
- 无法统一设置优先级
- 出问题难以定位是**哪个 SDK** 造成的

## 二、监控与创建流程原理

### 线程创建的唯一收口点

不管 Java 层怎么写（`new Thread` / 线程池 / 反射），最终**都绕不过 `Thread.start()`**：

```
Thread.start()
  → nativeCreate(this, stackSize, daemon)          [java_lang_Thread.cc]
    → Thread::CreateNativeThread(...)              [thread.cc]
      → pthread_create(...)                        ← 唯一的底层出口
```

线程池创建线程也只是 `ThreadFactory` 里调 `new Thread`。

**推论：Hook `pthread_create` 就能捕获所有线程创建，包括三方 SDK 的。**

### Hook 方案选型

| 方案 | 兼容性 | Hook 范围 | 性能 |
|---|---|---|---|
| GOT Hook | 优 | 差 | 优 |
| Inline Hook | 差 | 优 | 优 |
| Trap Hook | 优 | 优 | 差 |

**取舍逻辑（值得作为面试素材）**：如果这是**线下排查工具、不发布线上**，则兼容性无所谓 → 选 **Inline Hook** 求范围最广。
反之要上线，只能选 GOT Hook。

在 hook 点打印 **Java 层堆栈**，即可建立「新线程 ↔ 创建者堆栈」的映射。

### 线程数量限制不是固定值

取决于 `RLIMIT_NPROC`、`threads-max`、cgroup 限制、设备而定。
「几百上千个」是经验观察，**不是硬阈值**，面试别说死。

## 三、解决方案（四层防线 + 一个方向）

### 第一层：规范层 —— 治自家代码，成本最低，先做

建立统一线程池收口，禁止业务裸用 `new Thread`。

⚠️ **但「收口」收的是治理，不是物理池。** 不要把所有 IO 汇进一个池 —— 原因见下。

**先看反例：为什么「全 App 一个 IO 池」是错的**

三个硬伤（本项目实测）：

1. **队头阻塞**：FIFO 队列里，前面堵 4 个 800ms 的磁盘任务，后面 20ms 的网络请求
   要等 **839ms**。同一批任务改为分池后只需 **3ms**。
2. **下游资源异构**：网络受共享带宽约束、磁盘随机 IO 队列深度低、SQLite 是单写者。
   用一个并发数服务三种资源，对每种都是错的。
3. **全局故障面**：一个 SDK 失控提交慢任务，全 App 的 IO 一起瘫痪 ——
   等于在另一个层面重建了「线程滥用」本身。
4. **`maximumPoolSize` 是死配置**：`new LinkedBlockingQueue()` 容量是
   `Integer.MAX_VALUE`，而 `execute()` 的扩容条件是「队列满」，永不成立 →
   实际并发上限恒为 `corePoolSize`，写 `max=16` 是自欺。要用**有界队列**。

**正确形态：一个治理入口 + 多条按下游资源划分的泳道**

| 泳道 | core/max | 队列 | 依据 |
|---|---|---|---|
| net | 4 / 8 | 32 | 移动端带宽是共享管道，加并发只是均分；射频 race-to-sleep 要求集中突发 |
| disk | 2 / 4 | 16 | 手机 UFS/eMMC 随机 IO 队列深度低，加并发只推高**所有**请求延迟 |
| db | 1 / 1 | 64 | SQLite 单写者（WAL 下亦然），>1 纯粹在 DB 锁上排队 |
| bg | 1 / 2 | 128 | 后台预取/上报，低优先级可牺牲延迟 |

**线程数怎么定（别背公式）**：服务器公式 `核数 × (1 + W/C)` 追求 CPU 利用率最大化，
移动端目标是「延迟 + 功耗」，故意不这么算。正解是 **Little's Law 从低端机实测**：
并发数 = 到达率 λ × 任务时长 W，按 P99 加余量。eMMC 机型的 λ 和 W 会同时变差。
（另可对齐 OkHttp `maxRequestsPerHost = 5` 这类成熟惯例。）

**拒绝策略别用 `CallerRunsPolicy`**：泳道可以被主线程提交，饱和时让主线程去跑 IO
任务 = 直接 ANR；而且它拦不住无界队列导致的堆积（那才是真 OOM 来源）。改用
`AbortPolicy`，把背压显式抛回调用方，由它决定丢弃 / 降级 / 上报。

**静默输入之外，加调用方配额**（`quotaPerCaller`）：挡住「一个模块吃满整条泳道」。

治理能力（命名 / 配额 / 监控）集中在入口层：

**必须显式提供 `ThreadFactory`**，做到：

1. 语义化命名（`app-net-1` 而非 `pool-1-thread-1`）
2. 设置 `daemon`
3. 设置优先级 —— ⚠️ **只走 `android.os.Process.setThreadPriority` 一条路径**，
   不要再设 `Thread.setPriority`。实测二者落到同一个内核 nice，同时设是重复，
   还会互相覆盖（本项目 `bg` 泳道就被静默改过优先级）。
   另注：`Thread.setPriority` 够不到 nice < -8 的实时区间，而音频需要 -19。
   陷阱：`setThreadPriority` 作用于**当前线程**，必须包一层在新线程的 `run` 里调用。

> 默认工厂产出的 `Thread-7` / `pool-1-thread-1` 是后续监控失效的根源 —— 根本不知道是谁创建的。

配套：**自定义 Lint 规则**检测 `new Thread` / `Executors.newXxx`，卡在 CI 上，比 code review 可靠。

### 第二层：监控层 —— 先能看见，否则无从下手

**A. Java 层采样（零侵入）**

```kotlin
Thread.getAllStackTraces().keys.forEach { thread ->
    Log.d(TAG, "${thread.name} state=${thread.state}")
}
```

返回 `Map<Thread, StackTraceElement[]>`，适合线上 APM 做趋势统计和现场快照。

**B. Native Hook `pthread_create`（定位元凶的杀手锏）**

这是唯一能回答「**到底哪个 SDK 创建的**」的手段，因为它绕不过去。

**C. ASM 给匿名线程命名**

用字节码插桩把无参构造替换为带 name 的构造，把调用者类名通过 `LdcInsnNode` 塞进去：

| 转换前 | 转换后 |
|---|---|
| `Thread()` | `Thread(String)` |
| `Thread(Runnable)` | `Thread(Runnable, String)` |
| `Thread(ThreadGroup, Runnable)` | `Thread(ThreadGroup, Runnable, String)` |

参考实现：滴滴 Booster 的 `booster-transform-thread`。
效果：线上抓到的线程名直接自解释，不用对着 `Thread-37` 猜。

### 第三层：收敛层 —— ASM 统一线程池

**核心洞察：不统一 Thread，而是统一 Runnable 的执行环境。**

为什么不能直接替换 Thread？因为 Thread 创建依赖**局部变量表**：

```bash
NEW java/lang/Thread
DUP
INVOKEDYNAMIC run()...        # lambda → Runnable
INVOKESPECIAL Thread.<init>   # 隐藏消耗栈顶的 Thread 引用（DUP 的原因）
ASTORE 2                      # ← index 依赖上下文！无法通用插桩
```

`ASTORE` / `ALOAD` 的下标由方法环境决定（静态方法 0 是第一个参数，实例方法 0 是 this），所以对 Thread 做通用替换会踩坑。

**而 Runnable 是干净的突破口** —— 把 `INVOKESPECIAL Thread.<init>` 替换为自己的 `MyThread`：

```kotlin
class MyThread(private val runnable: Runnable) : Thread(runnable) {
    override fun start() {
        // 不真起线程，改丢进统一池
        ThreadHelper.runInCustomPool(runnable)
    }
}
```

配套需补 `CHECKCAST` 维持类型契约（原指令返回 Thread，现在返回 MyThread）。

**对三方 SDK 的额外手段：**

- ASM 插件可转换依赖中的 class（**前提：SDK 未加固/加壳**，加固过的插不进去）
- 运行时 Hook `Executors.defaultThreadFactory()` 与 `ThreadPoolExecutor` 构造，注入自定义 `ThreadFactory`，把三方池也纳入管控
- 定向收口：如 OkHttp 的 `Dispatcher.executorService` 可直接 setter 替换

### 第四层：运行时防御 —— 兜底

- **压缩栈大小**：`new Thread(group, runnable, name, stackSize)` 的第 4 个参数直达 `pthread_attr_setstacksize`。
  按业务需要从默认 1MB 收到 256KB 甚至 64KB（下限 `PTHREAD_STACK_MIN` 16KB），
  **虚拟地址空间占用直接砍一个数量级** —— 32 位设备最实惠的一招。
  ⚠️ 别收太小，深递归会栈溢出。
- **限流降级**：全局统计活跃线程数，超阈值时拒绝新建 / 走队列 / 复用
- **后台纪律**：后台任务改用 **WorkManager**（系统统一调度、可合并、受 Doze 管控），而不是自己 `new Thread` 常驻

### 根本方向：用协程替代线程

Kotlin 协程在这一点上是**降维打击**：

- 协程是用户态调度的**续体（continuation）**，跑在共享线程池上
- **每个协程不 reserve 1MB 虚拟栈**
- 几千个协程跑在几个线程上完全没问题；几千个 Thread 早就崩了

落地方式：用 `CoroutineDispatcher` 收口替代线程池。
`Dispatchers.IO` 有上限保护（默认 64，可用 `limitedParallelism` 调整）。

⚠️ **边界**：协程拦不住三方 SDK 的线程创建。
所以 **自家代码用协程，三方 SDK 仍需 ASM / Hook 兜底** —— 两者互补，不是替代关系。

## 四、落地优先级

```
1. 先测量  ── Thread.getAllStackTraces() 采样 + 线程命名规范
             摸清基线：有多少线程、谁造的
2. 再定规范 ── 统一线程池 + Lint 卡口（治自家代码，低成本高收益）
3. 然后收口 ── ASM 匿名线程命名 → 收敛到统一池（治历史代码）
4. 最后兜底 ── Hook pthread_create 定位顽固 SDK + 压缩栈 + 限流
```

**顺序不能反。没有测量就上插桩，等于不知道自己在优化什么。**

## 五、面试要点速记

**被问「线程多了有什么危害」**
→ 分四层答（内存/CPU/稳定性/架构），但**主动校正两个常见误区**：
① 1MB 是虚拟地址空间不是物理内存；② 上下文切换的代价主要是 cache/TLB 失效，且要分 IO 密集 / CPU 密集讨论。

**被问「三方 SDK 改不了怎么办」**
→ 这是核心考点。答四层防线，强调 ASM 能处理**依赖中的 class**，Hook 能拦**运行时行为**。

**被问「怎么定位是哪个 SDK」**
→ 从 `Thread.start()` → `pthread_create` 的调用链切入，说明这是唯一收口点，
再说 Hook 方案选型（线下工具选 Inline，线上只能 GOT）。

**被问「为什么不直接统一 Thread」**
→ 答字节码层面：`ASTORE` 下标依赖局部变量表，无法通用插桩；
所以转而对 Runnable 下手，统一执行环境。
