> 「我做的不是『把某个接口调快』，而是给 App 搭了一层**可感知、可度量、可降级**的网络治理层。

## 1. 全局模型：先把「时间花在哪」讲清楚

一次 HTTPS 请求的耗时拆解：

```
DNS解析 → TCP握手 → TLS握手 → 发送请求 → 服务端处理 → 首字节 → 响应传输
 20~200ms  1×RTT     1~2×RTT              业务耗时              受带宽/丢包影响
```

**弱网的三个特征是：高延迟、高丢包、带宽不稳定，外加「假连接」**（WiFi 满格但实际不通）。
弱网下 RTT 从 50ms 涨到 500ms+，丢包 2%~10%，此时**握手次数与往返数**成为最大杀手。

由此得出的五条总原则：

1. **减少连接数**（少握手）
2. **减少往返数 RTT**（少等回合）
3. **减少传输数据量**（少传字节）
4. **提前准备**（预连接、DNS 预解析）
5. **对抗不确定性**（质量感知、动态策略、多路备援、优雅降级）

> 面试点：原则 1-4 是「强网优化」，原则 5 才是「弱网专项」。很多人把两者混为一谈。

## 2. 分层落点（本项目怎么对应）

| 层 | 职责 | 本项目文件 | 关键点 |
|---|---|---|---|
| 感知 | 判断「现在是不是弱网」 | `NetworkQuality.kt` + `NetworkScoring.kt` | 静态类型 + 动态质量融合；策略抽成纯函数 |
| 度量 | 定位「慢在哪、慢多少」 | `NetEventListener.kt` + `NetMetrics.kt` | 分阶段 + 分位数；EventListener 而非 Interceptor |
| DNS | 省掉解析、避开坏 IP | `InterviewDns.kt` + `DnsResolver.kt` | TTL 缓存 + 多 IP 排序 + 坏 IP 熔断 |
| 策略 | 动态超时、幂等重试 | `AdaptiveRetryInterceptor.kt` + `NetConfig.kt` | 自适应超时 = f(RTT)；退避+抖动 |
| 收口 | 一份连接池、一份度量 | `NetClient.kt` | 唯一 client 工厂；按下游资源分档 |

## 3. 逐层展开（面试主体）

### 3.1 感知层：为什么「网络类型」不可信？

**两个层次缺一不可：**

- **静态类型**：`ConnectivityManager` 告诉我们 WiFi/4G/无网。它快、免费、事件驱动，
  但**不可信** —— 「WiFi 满格却不达」是最常见的假连接（酒店门户、断网的路由器）。
- **动态质量**：由真实请求结果回喂的滚动 RTT/成功率。它慢半拍，但反映**真实可达性**。

融合成一个 `level`，作为**策略层唯一判据**：

```kotlin
when (NetClient.networkQuality().level) {
    OFFLINE  -> showOfflineCache()
    WEAK     -> loadFirstPageOnly()      // 只拉首屏 / 低清图 / 关预加载
    MARGINAL -> loadNormalPage()         // 正常，但不预取
    GOOD     -> loadWithPreload()        // 全量 + 预加载
}
```

**两个设计点值得讲：**

1. **假连接检测**：`有网 && 样本≥3 && 成功率==0 → WEAK`。
   这条规则是「感知必须结合真实请求」的最有力证据 —— 单看 WiFi 图标会误判。
2. **平滑 RTT 用中位数而非均值**：DNS 慢一次的样本不该把整体判成弱网（抗长尾）。

**为什么把打分抽成纯函数（`NetworkScoring`）？**
因为它原本嵌在 Android `object` 里 —— 一被引用就触发 ConnectivityManager 回调注册，
**没法在 JVM 上单测**。抽成纯函数后全部分支秒级验证，不需要设备、不需要网络。
这和本仓库对 native 代码的纪律一致：**能算错的逻辑必须可离线测试**。

> 阈值（100ms/300ms/0.6）我都在代码里标了「经验值，非实测标定」——
> 面试时主动说这句，比假装它是推导出来的更加分。

### 3.2 度量层：为什么必须用 EventListener？

这是我最想讲的**技术判断点**。

**错误做法**：在 Interceptor 里 `System.nanoTime()` 打点。
**问题**：它只能测到**应用拦截器链内**的时间，天然不包含 DNS、TCP、TLS ——
而弱网优化要定位的恰恰是这三段。

**正确做法**：`EventListener` 是 OkHttp 埋在网络栈**内部**的钩子，每段边界都回调。
这就是「请求耗时拆解图」在 OkHttp 里的唯一准确实现方式。

**里面有一个极易写错的点**（我踩过并写在代码注释里）：
`connectEnd` 是**整个连接（含 TLS）完成**才回调。所以要取「纯 TCP 握手耗时」，
必须用 `secureConnectStart` 这个边界截断，否则会把 TLS 时间算进 TCP。

另一个准确来源：**连接复用率**。判据是「本次 Call 有没有触发 `connectStart`」——
`connectionAcquired` 时若从未 `connectStart`，即复用了连接池。

**分位数怎么算**：最近邻法（不插值）+ 1-based nearest-rank。
> 我在这里抓到一个真实 bug：原先用 0-based `N*p/100`，N=10 时 P50 会返回**第 6 个值**，
> 分位数系统性偏高一位。这类 off-by-one 不会报错，只会让监控悄悄骗人。
> **主动讲这个 bug 是加分项** —— 证明我真的在看数据，而不是把指标当装饰。

`NetMetrics` 只保留最近 200 条（是「近期体检」不是「永久账本」），输出：
P50/P90/P99、各阶段均值、连接复用率、缓存命中率，以及**逐条记录**（每条的网络错误长什么样）。

### 3.3 DNS 层：缓存 + 多 IP + 坏 IP 熔断

**问题**：DNS 解析慢（弱网下占整体 10%+ 且超时率高）、劫持、调度不精准。

**手段**：

- **TTL 缓存**：命中即 ~0ms，弱网最直接收益。
- **多 IP 排序**：OkHttp 按返回顺序依次尝试，把坏 IP 沉底就能避开大部分损失。
- **坏 IP 熔断**：DNS 返回的 IP 里混着坏 IP（黑洞路由/机房故障）是常态。
  不加熔断，每次连接都先试那个坏 IP，用户要为**一条线路的故障**付出整个连接超时。

**三个必须讲清的判断：**

1. **熔断是「排序」不是「过滤」**。如果全部 IP 都在熔断期就把列表清空，
   请求会直接失败 —— 熔断的目的是「少走弯路」，不是「拒绝服务」。这个边界极易写反。
2. **熔断时长递增**（1s→2s→4s…上限 60s）。「坏 IP」可能是瞬时的（线路抖动），
   一次性熔断很久会让已恢复的线路长期不可用。
3. **健康信息只能从建连侧回报**。`Dns` 只负责给地址，它**看不到**后续哪次连接成功。
   所以用 `EventListener.connectFailed` 把「哪个 IP 连不上」回报给熔断表 —— 这是一个真实的模块边界。

**诚实点（面试官很吃这套）**：我实现的**不是 HTTPDNS**。
它走 UDP 明文 53，能拿多 IP 与 TTL、能熔断，但**不能防劫持/投毒**，也不能按用户位置调度。
真 HTTPDNS 需要 DoH/DoT（HTTPS/TLS 传输）+ 服务端就近调度，是另一个模块的量级。

> 追问「为什么自己解析报文」：因为 `InetAddress.getAllByName` 只能走系统 DNS，
> 无法指定服务器、拿不到 TTL。自己实现报文层虽然啰嗦，但换来对整条解析链路的控制权。

### 3.4 策略层：自适应超时 + 幂等重试

**要纠正的两个常见错误：**

**错误 A：一刀切超时。** 写死 10s 的问题 —— 强网下白等，弱网下不够，
一次慢请求还占满泳道。正确做法用**实时 RTT 反推**：

```
timeout = max(base, k × 平滑RTT)   // k = 3，再夹到 [base, max]
```

为什么乘 3：中位数不能代表最坏一次，一段可用链路里 P99 往返通常是中位数的 2~3 倍。
（同样是经验值，代码里标注了。）

**错误 B：无脑重试。** 重试非幂等请求会重复下单；不加退避的重试在抖动时形成**重试风暴**。

幂等判定按 HTTP 规范：
- `GET/HEAD/OPTIONS/TRACE` safe → 可重试
- `PUT/DELETE` idempotent → 可重试
- `POST/PATCH` → **默认不重试**，除非带 `Idempotency-Key`（Stripe 等支付接口的通行约定）

**退避**：`300ms × 2^(n-1) × 抖动[0.5,1.5)`，上限 2s。
抖动为什么必要：大量客户端同时失败时，无抖动会让它们**同步**重试形成周期冲击波，
被重试的流量比原故障还大。

**只重试「临时性」错误**：408 / 429 / 502 / 503 / 504。
4xx 业务错误重试 100 次还是 400，纯浪费流量。

**放对层**：用应用层 Interceptor 而非 network interceptor —— 后者跑在「单次网络往返」内，
看不到建连失败，也不该重试整个 Call。这是重试放错层最常见的错误。

### 3.5 收口层：为什么必须有「唯一 client」

改造前，本项目有**两套各自为政的 client**：图片下载器自建一个、Retrofit 用默认的（等于又一个）。
后果和「每个页面 new 一个线程池」一模一样：**连接无法复用、DNS/连接池各建各的、度量各测各的**。

所以 `NetClient` 成为全 App **唯一**允许 `OkHttpClient.Builder()` 出现的地方。
两个既有调用方改为取用：`ImageDownloader → NetClient.downloads`、`Retrofit → NetClient.shared`。

**分档的依据（这是关键，不是随意分两个）：**

| 档 | 瓶颈 | 超时 | 重试 |
|---|---|---|---|
| API | **RTT 受限** | 8s 自适应 | 3 次 |
| DOWNLOAD | **带宽受限** | 60s（上限 180s） | **1 次**（大文件重下比传完更浪费） |

两档是**两个 client、两份连接池**，但**共享同一份 DNS 与 EventListener** ——
所以 DNS 缓存、坏 IP 熔断、分阶段度量是全 App 一致的。

> 一句话总结收口哲学：**收的是治理与观测，执行参数按下游资源分档。**
> 这和本仓库线程池「治理收口、执行分道」是同一个设计哲学。

## 4. 弱网治理专项

### 4.1 三特征 → 三类手段

| 弱网特征 | 手段 |
|---|---|
| 高延迟 | 自适应超时、预连接、减少 RTT |
| 高丢包 | 幂等重试+退避、多 IP 竞速、坏 IP 熔断 |
| 带宽不稳 | 数据降级、图片降清晰度、缓存先显 |
| **假连接** | **动态质量感知**（系统类型 + 真实请求结果融合） |

### 4.2 分级降级（按 `level` 一刀切）

| 维度 | 弱网降级 |
|---|---|
| 数据 | 只拉首屏/前 N 条，关闭预加载 |
| 图片 | 低清/WebP 小图，骨架屏 → 逐步加载 |
| 上行 | 埋点/日志本地排队，强网/WiFi 再批量上报 |
| 交互 | 提前提示「网络不佳」，允许离线操作后续同步 |

### 4.3 弱网下重试与泳道的关系（本项目特有的坑）

重试会**延长单个任务占用泳道线程的时间**。若不加总预算，弱网下 3 次重试 × 30s
会把泳道拖满，反过来触发泳道配额拒绝。所以重试同时受 **per-call 超时**与**次数上限**双重约束，
且退避睡眠也设上限。

## 5. 与线程治理的协同（本项目特色，加分项）

网络只是「跑得怎么样」，还要有「谁在什么线程上跑」：

- 所有网络任务提交到 `ThreadPools.network` 泳道，**不在 Activity 里 new Thread**。
- `execute()` 返回 `Boolean`：`false` 是**背压信号**（配额满/队列满），必须处理，
  否则任务静默消失、指标涨了却没人降级。
- 泳道 net 档：core=4 / max=8 / queue=8 / 每调用方配额=16。
  **泳道并发 ≠ 网络并发**：4 个泳道线程把请求交给 OkHttp，OkHttp 自己还有
  Dispatcher（maxRequests=64 / maxRequestsPerHost=5）与连接池，两层是**叠乘**关系。

> 面试点：能讲清「泳道背压」和「网络并发」是两层，说明真的做过多层治理，不是只会调 OkHttp。

## 6. 量化与验证（面试官最想听的部分）

**「没有度量就没有优化」在这个项目里是硬约束，不是口号。**

| 类别 | 证据 |
|---|---|
| 单元测试 | 网络层纯逻辑 **17 个**用例；Rust kernel **36 个**；JNI 薄层 **3 个** |
| 抓到的真 bug | 分位数 0-based off-by-one（P50 返回第 6 个值） |
| 真机实验页 | 「网络优化 Lab」7 个按钮，走完整证据链 |
| APK 体积实测 | 13.1 → 13.5 MB（新增 netlab .so 343 KB） |
| 对照实验 | 系统 DNS vs 自定义 DNS（解析耗时/IP 差异/热缓存 ~0ms） |

**测试策略的划分**（这是我最想强调的工程观）：

- 「**会算错但不会崩**」的逻辑 → 抽成纯函数，JVM/host 秒级单测
  （打分、退避区间、幂等判定、分位数、DNS 报文编解码、取消状态机、线格式）。
- 「**需要真机**」的部分 → 用实验页做对照（EventListener 真实回调时序、连接复用、网络切换）。

弱网优化最容易出错的地方不是「请求发不出去」，而是「**策略算错了却不报错**」——
比如重试把非幂等的 POST 重发两遍，上线看指标一切正常，直到用户被重复下单。
这类 bug 只有秒级单测拦得住。

## 7. 进阶：传输层升级（如果面试官想聊深入）

**问题**：OkHttp 不支持 HTTP/3（官方 issue 已 closed as not planned）。想要 QUIC 只有两条路。

### 7.1 Cronet（不写 Rust 就有 HTTP/3）

官方有 `google/cronet-transport-for-okhttp`，做的正是「把另一套 native 网络栈统一到 OkHttp 之下」。
我**实测**了体积：

| 方案 | arm64 APK 增量 |
|---|---|
| `play-services-cronet` 提供方（AAR 仅 **90 KB**） | 百 KB 级（native 由设备 GMS 提供） |
| `cronet-bundled` 自带 native | **+7.0 MB**（当前 release 才 9.2 MB，**+77%**） |

**关键结论**：用 Cronet 后，OkHttp 核心（缓存/重试/网络拦截器）**整体旁路**，
`EventListener` 中间阶段不回调 —— **我们刚做的分阶段度量会失效**，证书固定必须重配。
而且官方适配器最新只有 0.1.1，还依赖 OkHttp 3.12.13。

### 7.2 Rust 自研（我实际搭了骨架）

**「统一到 OkHttp」的正确缝合点是 `Interceptor`，不是 `Call.Factory`。**
证据：CallFactory 模式会「bypassed completely」，连应用拦截器都不跑 ——
会让自适应重试拦截器**静默失效**（典型假绿）。

**代价（必须讲）**：只要传输换掉，OkHttp 的 DNS、连接池、EventListener 度量、证书固定
全部失效，都要在 Rust 侧重造。**这是自研和 Cronet 共同的代价**，
区别仅在于自研时你**能**重建分段度量，而 Cronet 给不了。

**线程治理难题**：quinn 需要 async runtime，runtime 会起自己的 event loop 线程，
**绕过 `thread-lint` 与泳道治理**。所以我的方案是 current-thread runtime + `block_on`，
让网络任务落在泳道线程上 —— 并且**在解决这个问题之前，我拒绝写 `fetch` 的空实现**
（那会是一个名字唬人、实则空转或偷偷起线程的假绿）。

**已落地的骨架**：`rust/netlab`（纯逻辑）+ `rust/netlab-android`（薄 JNI），
36 + 3 个单测，交叉编译出 9 个 JNI 符号的 .so 并确认打进 APK。

### 7.3 三条硬结论

1. 「统一到 OkHttp」可行，缝在 Interceptor；但换传输 = 失去 OkHttp 的 DNS/连接池/度量/证书固定。
2. **产品想拿 HTTP/3 → 用 Cronet**（零 Rust）；**想研究传输层 → 用 Rust 做独立实验模块，保留回退开关**。
3. Rust 不是「更强的网络优化工具」，它是「唯一能让你自己实现 QUIC 的语言」。除此之外多是治理成本。

## 8. 诚实的缺口（面试时主动讲，比被问出来加分）

| 缺口 | 现状 | 正解 |
|---|---|---|
| 非 HTTPDNS | UDP 明文，不防劫持、不精准调度 | 换 DoH/DoT 的 `Dns` 实现（改动点只有一处） |
| 无断点续传 | 下载档不重试，弱网大图中断即重来 | Range 分片 + 本地记录偏移 |
| 无 HTTP/3 / QUIC / BBR | OkHttp 不支持 | Cronet 或 Rust(quinn) |
| 无 Brotli | 只有默认 gzip | 加 `okhttp-brotli` |
| 参数多为经验值 | 阈值/系数/超时标了「待实测」 | 用真实分位分布回调 |
| 分段口径不可直接比 | QUIC 融合 TCP+TLS 握手 | 打标 `TransportKind`，汇总分开呈现 |

> 主动列出缺口，传递的信号是：**我知道自己的方案的边界**，而不是「我以为我做完了」。

## 9. 高频追问 & 应答

**Q1：为什么不用 Interceptor 测耗时？**
A：只能测到应用拦截器链内，天然不含 DNS/TCP/TLS —— 而这三段正是弱网优化要定位的。
EventListener 是 OkHttp 埋在网络栈内部的钩子，是唯一准确的实现方式。

**Q2：连接复用率怎么算准确？**
A：判据是「本次 Call 有没有触发 `connectStart`」。`connectionAcquired` 时若从未 connectStart，
即复用了连接池。这是唯一准确来源，不能靠「耗时短推断」。

**Q3：重试会不会把服务打垮？**
A：三重约束：只重试幂等方法、只重试临时性状态码、指数退避 + 随机抖动打破同步冲击波，
且总次数与总时长都有上限（还要考虑占用泳道线程）。

**Q4：为什么超时是 RTT×3 而不是直接给个固定值？**
A：固定值的两难 —— 强网白等、弱网不够。用实时 RTT 反推能自适应链路质量。
乘 3 是因为中位数不能代表最坏一次，P99 往返通常是中位数的 2~3 倍。

**Q5：弱网降级会不会影响强网用户？**
A：不会 —— 降级只由 `level` 触发，而 `level` 融合了真实请求质量。
样本不足时 WiFi/以太网默认 GOOD（乐观），只有蜂窝才保守一档。

**Q6：DNS 缓存时间长了好不好？**
A：两难。长 TTL 省电省流量，但故障/切流后长期指向旧 IP；短 TTL 响应快但查询多。
取了 60s 折中（移动端常见做法）。所以 TTL 是**策略值**，不是对服务端 TTL 的忠实翻译。

**Q7：怎么保证 native 的 DNS 解析结果是对的？**
A：DNS 报文编解码抽成纯函数做单测（构造最小合法报文，断言字段），
并校验事务 ID（防 UDP 上收到迟到响应 —— DNS 缓存投毒的应用层版本）。

**Q8：为什么要区分 API 档和下载档？**
A：瓶颈资源不同。API 是 RTT 受限，超时应对 RTT 敏感；下载是带宽受限，
超时要给足且**不该重试**（重下 3MB 比让它传完更糟）。用一套超时对两者都是错的。

**Q9：真机上怎么验证这一套有效？**
A：实验页做对照 —— 并发 10 次看连接复用率从 0% 升起（第二次起 reused=Y、各阶段为 -1）；
系统 DNS vs 自定义 DNS 的解析耗时与 IP 差异；逐条记录看每个失败长什么样。

**Q10：如果让你重做，会优先做什么？**
A：先做度量（EventListener + 分位数），再做策略。因为**没有度量，所有优化都是玄学** ——
你甚至不知道 P99 的 3 秒花在 DNS 还是 TLS。这也是我实际的落地顺序。

**Q11：Rust 传输栈的最大风险是什么？**
A：不是性能，是**安全与治理**。安全：证书固定必须在 rustls 里等价实现，漏了就是静默降级，
且不会报错。治理：async runtime 的线程会绕过既有的线程命名/配额协议。

**Q12：为什么说「Cronet 的补丁不完整」？**
A：它能给你 HTTP/3，但代价是 OkHttp 核心整体旁路 —— 缓存、重试、网络拦截器、
EventListener 分段度量全没了。而且适配器依赖陈旧（还绑 OkHttp 3.12.13）。
所以它是「拿功能」，不是「无损升级」。

## 10. 一页速查表

| 环节 | 强网优化 | 弱网专项 | 本项目落点 |
|---|---|---|---|
| 感知 | — | 质量评分、假连接检测 | `NetworkScoring`（纯函数，可测） |
| 度量 | 分阶段耗时 | 弱网单列 P99 | `NetEventListener` + `NetMetrics` |
| DNS | 缓存、多 IP | 坏 IP 熔断、系统兜底 | `InterviewDns` |
| 建连 | Keep-Alive、连接池 | 快速失败、多 IP 竞速 | `NetClient` + OkHttp 连接池 |
| 握手 | TLS1.3、Session 复用 | QUIC 0-RTT（未落地） | 见 C/A 文档 |
| 数据 | 缓存、增量更新 | 骨架屏+缓存先显、降级 | 按 `level` 分档 |
| 重试 | 幂等设计 | 指数退避+抖动、总预算 | `AdaptiveRetryInterceptor` |
| 收口 | 唯一 client | 按资源分档 | `NetClient` |

**一句话收尾**：

> 强网优化追求「更少往返、更小体积、更高复用」；弱网优化在此基础上，
> 通过**质量感知、动态策略、多路备援、优雅降级**对抗不确定性 ——
> 让体验从「依赖网络」变成「驯服网络」。而这一切的前提，是**先有度量**。
