## 0. 电梯稿（30 秒，先背熟这段）

> 「我做过 RN Bundle 的分包加载。核心问题是怎么让一个基础包和一个业务包，**在同一个 JS 运行时里**
> 各自独立构建、又能互相引用 —— 业务包 require 到 `react-native` 时，解析的是基础包注册的模块。
>
> 我的做法是：**module id 不用 Metro 默认的自增，改成文件路径的哈希**，这样两个工程无需共享任何
> 状态就能算出同一张 id 表；业务包构建时走 `modulesOnly` 只出模块定义，把基础包已有的部分剥掉，
> 但**依赖引用保留**；原生侧用一个自定义 `JSBundleLoader` 顺序加载两个 bundle。
>
> 最终业务包 4.8KB，基础包 868KB，业务包里基础包的模块定义残留 0 个 —— 真机上两个组件
> 跑在同一个运行时里，互相能引用。」

**这段为什么有效**：一句话点出难点（跨工程 id 一致）、给了具体手段（路径哈希 / modulesOnly）、
给了可验证数字（4.8KB / 0 残留）。**数字是这项目最大的加分项，一定要说出来。**

## 1. 讲述主线（3 分钟版，按 STAR 走）

### S｜背景与问题

「RN 默认把整个 App 打成一个 bundle。我们（按业务需要）想把基础库和业务代码拆开 ——
基础包跟着 App 发版，业务包可以独立更新，业务侧改一行代码不用重发 App。」

**难点在哪**（这里是真正要讲清楚的部分）：
「拆开容易，难在**两个包是两个独立构建的产物**：两个工程、两套 node_modules、两张依赖图。
但运行时只有一个 —— 业务包 `require('react-native')` 的时候，必须能解析到基础包里注册的那份。
而 Metro 默认的 module id 是**自增整数**，按模块被访问的顺序发号；两个工程访问顺序必然不同，
同一个文件会拿到不同 id，映射就无从谈起。」

### T｜我做了什么

「所以第一件事是把 id 变成**文件身份的纯函数**：

```
id = parseInt(sha1(key).slice(0, 8), 16) % 2^20
```

key 是工程内相对路径 —— 但这里有个坑我踩过：如果 key 就是相对路径，那两个工程里都有的
`index.js`、`App.tsx`、`app.json` 会算出**同一个 id**，业务包的入口会被误判成「基础包里已经有」
而被整个过滤掉，入口直接消失。所以 key 我分了两类：`node_modules` 下的**跨工程共享**，
工程自有源码按 `appId` 加前缀**隔离**。」

「第二件事是业务包的剥离。这里有个反直觉的点：**剥离只删『模块定义』，不删『模块引用』**。
业务包里 `react-native` 的 id 必须留在依赖表里 —— 因为编译产物是靠 `r(下标)` 取依赖的，
把引用也删掉，运行时就取到 `undefined` 崩了。」

「第三件事是原生侧：**一个自定义 `JSBundleLoader` 顺序加载两段脚本**。
关键是不能用「同步加载」来保证顺序 —— 我读源码发现 `loadSynchronously=true` 会在**调用线程**
（也就是主线程）上直接执行 JS。用 `false` 两次投递进同一条 JS 队列，先入先出，顺序本来就有保证。」

### A｜怎么保证做对了

「我把『业务包里不含基础包内容』做成了**可复算的三层判据**，而不是靠看：

| 层 | 判据 | 结果 |
| --- | --- | --- |
| L1 定义层 | 业务包里不得存在 id 属于基础包的 `__d` | 基础包 489 个定义，残留 **0** |
| L2 体积层 | 业务包必须显著小于基础包 | 4.8KB / 868KB = **0.5%** |
| L3 拼接执行 | 基础包 + 业务包拼起来在 Node 里**真跑一遍** | 注册 4 个模块，入口能沿「业务→基础→react-native」解析 |

「L3 是最有价值的 —— 前两层只看静态文本，**拼接执行才能暴露『id 对不上』『依赖取到 undefined』**
这类问题。Node 里没有原生桥，所以最后会停在 `__fbBatchedBridgeConfig is not set`，
这属于**预期**，说明 JS 层模块链路已经通了。」

### R｜结果

「真机上两个 launcher 入口、两个组件跑在**同一个 pid、同一个运行时**里。日志各有一行
`Running "RnBundleSplit"` 和 `Running "BusinessApp"`。业务界面的分数是业务包自己的代码算的，
点按钮会走业务包的 `useState` 重渲染 —— 说明 **React 运行时来自基础包、业务逻辑来自业务包，
在同一次渲染里协同工作**。」

## 2. 三种背景的面试官，各该讲什么

面试官背景不同，关心点完全不同。**开场先看对方话头往哪走，再决定往哪个方向深挖。**

### 2.1 如果对方是 Android 原生背景

**重点词**：`JSBundleLoader`、`ReactInstanceManager`、桥接模式、主线程安全、读源码定方案。

要主动亮出的点：

- 「我自定义了 `JSBundleLoader` 的子类，重写 `loadScript()`，在里面调两次
  `delegate.loadScriptFromAssets()`。`ReactInstanceManager` 一次运行只调 `runJSBundle()` 一次，
  所以一个 loader 加载两段脚本是成立的。」
- 「踩过 builder 的坑：`setJSBundleLoader` 会清掉 `mJSBundleAssetUrl`，反过来
  `setBundleAssetName` 会清掉 `mJSBundleLoader` —— 顺序设反了 loader 就没了。而且 `build()`
  里有个断言：`useDeveloperSupport`、`bundleAssetUrl`、`bundleLoader` 三者至少有一个。」
- 「我特意关掉了 dev support。因为如果它为真，`recreateReactContextInBackgroundInner()`
  会优先去连 Metro，把我装的 loader **绕过去**。关掉后 debug 也固定走 assets，可离线复现。」
- **主线程安全**（这条最加分）：「我一开始想用 `loadSynchronously=true` 强行保证顺序，
  读源码后改掉了 —— 它走 `loadBundleSync`，**在调用线程上直接执行 JS**，
  从主线程调等于在 UI 线程跑整个 bundle。用 `false` 走 `runOnExecutorQueue`，
  两次投递进同一条队列，靠 FIFO 保证顺序，这才是对的。」

**能接的话题**：桥接模式 vs 新架构（bridgeless 走 `ReactHost.loadBundle`，路径不同，我的方案不适用）。

### 2.2 如果对方是跨端 / RN 方向

**重点词**：Metro serializer 扩展点、module id 机制、`modulesOnly`、`runtimePreCode`。

要主动亮出的点：

- 「我没有另写一套打包器 —— 走的是 RN CLI 完全同一条路径 `metro/src/Server` 的 `build()`，
  只覆写 `serializer.createModuleIdFactory`。这样 transformer / resolver / minify 行为跟标准打包一致，
  不会走出一个『只有我的工具认识』的怪 bundle。」
- **业务工程接入是零侵入的**：「业务工程只需要在 `metro.config.js` 尾部包一层 preset，
  原始配置完全不动，而且 `uninit` 能还原 —— 有备份文件，幂等，重复执行不会叠加包装。」
- 「业务包必须走 `modulesOnly: true`。因为基础包和业务包共用同一张全局模块表，
  如果业务包也带 runtime prelude，里面的 `clear()` 会 `modules = new Map()`，
  把基础包注册的几百个模块**整个清空**，业务代码一 require react-native 就崩。」
- 「我用 `@babel/parser` 解析产物，但**只取 AST 的 range（区间）**，用 splice 精确摘除语句、
  **不做代码生成**。为什么？重新生成代码会改变全部原有字节、**破坏 sourcemap 的行映射**。
  只取区间就能做到『除了被摘掉的那几段，其余字节原样不动』。」

**能接的话题**：`inlineRequires`（RN 默认开启，会把 `require('./y')` 内联成 `r(ID)`，
所以依赖表要同时看 `dependencyMap` 和语句里的 `r(N)` 调用）。

### 2.3 如果对方是工程化 / 架构基建方向

**重点词**：契约设计、可验证性、幂等接入、边界诚实。

要主动亮出的点：

- **mapping 是一份契约**：「mapping 一旦生成，就是业务工程唯一需要知道的东西 ——
  它不需要基础包源码、不需要基础包 bundle、不需要 node_modules 版本对齐，
  拿到 mapping 就能算出完全一致的 id、并且知道哪些该剥。」
- **可验证性**（前面 L1/L2/L3 表）。
- **宁可构建失败，也不静默出错**：「哈希取模理论上会碰撞，489 个模块时概率约 0.11% ——
  量级可观，不能忽略。所以我在生成 mapping 时显式检测碰撞，**有碰撞直接抛错**并提示换盐值，
  读 mapping 时再校验一次 id 唯一性。宁可构建失败，也不出一个 id 悄悄指错的 bundle。」
- **接入可逆**：「工具用软链进业务工程，不写 `package.json`、不装依赖；
  `init` 会备份 `metro.config.js`，`uninit` 一键还原 —— 试用成本低，卸载干净。」

## 3. 高概率追问 · 标准答案

> ⚠️ 按出现概率排序。**前两条几乎必问，务必背熟。**

### ⭐ Q1：RN 官方不是有 RAM bundle / 分包机制吗？为什么不用？

**这是第一追问，答不好整场崩。**

先正面承认（很重要，别硬说官方没有）：

「有的，RN 官方有 RAM bundle 和 segment 机制：`registerSegment(segmentId, definer, moduleIds)`
配合 `nativeRequire(localId, segmentId)`，模块 id 被拆成 `segmentId << 16 | localId`，
主包注册 segment 定义表，加载到未注册模块时由 native 回源拉对应分片。」

再说我的差异与**场景适配性**：

「官方机制的形态是**运行时分片拉取** —— 分片是同一份构建、同一个 id 空间里切出来的，
需要 native 侧配合按 segment 回源。它解决的是**按需加载、减小首包**。

我这个场景要的是**两个工程独立构建、独立发版**：基础包跟 App 走，业务包由业务工程自己
构建、能独立更新。这要求 id 在两个**互不通信的构建**之间都算得出来 —— 所以我把 id 做成
**路径哈希的纯函数**，这是官方 scheme 里没有的部分。」

最后给**诚实结论**：

「所以准确说：我验证的是**跨工程 id 契约 + 顺序加载**这条链路。如果目标是**同一工程内**
减小首包，用官方 RAM bundle 更合适、也不用自己维护 mapping。」

> 💡 这样答的好处：既证明你读过源码、知道官方方案，又清楚自己方案的定位，
> 还主动划了边界 —— 面试官会觉得你**不吹**。

### ⭐ Q2：为什么要自己算 id？不能让两个工程用同一个 id 策略吗？

「Metro 默认 `createModuleIdFactory` 是按**模块被访问顺序**发号的自增整数。
两个工程的依赖图不同 → 访问顺序不同 → 同一个文件拿到不同 id。这不是『策略不统一』的问题，
是**自增本身就依赖运行时状态**，天然不可跨构建对齐。要跨工程对齐，id 必须退化成
**不依赖任何共享状态的纯函数** —— 我选了路径哈希。」

### Q3：哈希会不会碰撞？碰撞了怎么办？

「会。489 个模块时概率约 `n²/(2·2^20) ≈ 0.11%`，量级可观，不能忽略。
所以我没有『降低概率』而是**让碰撞不可能静默通过**：生成 mapping 时检测到碰撞直接抛错，
提示换 `--id-salt` 重新生成（两个工程必须用同一个盐）；读 mapping 时再校验一次 id 唯一性。
宁可构建失败，也不出一个 id 悄悄指错的 bundle。」

### Q4：业务包为什么不能被单独加载？

**这题背后是我查出来的一个真问题**（如果面试官看代码，一定会看到）：

「严格说，**当前实现里业务包确实不能单独加载**，而且我发现代码注释和实际行为不一致，
如实说：工具里有个 runtime 垫片，注释写的是『让产物可单独加载』，但它被追加到文件**末尾**，
而 `__d` 定义在文件**开头** —— 单独加载时第一行就报 `ReferenceError: __d is not defined`，
垫片根本没机会生效。我实测验证过这一点。

要真正支持，垫片得插到文件最前面（工具里 `stripBaseModules` 的 `shim: true` 分支就是这么做的，
只是 `split` 命令传了 `false`）。我把它记进文档作为待办，没有擅自改 —— 因为当前
**与基础包配合**的场景下这个垫片本来就是 no-op，改了不影响主链路，优先级不高。」

> 💡 **这题是加分题**。主动暴露一个自己查出来的不一致，比藏起来强得多 ——
> 体现「文档与实现要对齐」的工程素养。**但注意别主动提，等被问到再说**。

### Q5：为什么不用同步加载保证顺序？

「我一开始就是这么想的，读源码后改掉了。`loadSynchronously=true` 走 `NativeToJsBridge::loadBundleSync`，
**在调用线程上直接执行 JS** —— 从主线程调用它，等于在 UI 线程上跑完整个 bundle。
用 `false` 走 `runOnExecutorQueue`，投递到那条 JS 线程队列，
两次投递**先入先出**，顺序本来就有保证。RN 自己的 split bundle 加载器也用 `false`。」

### Q6：两个 bundle 进同一个运行时，会不会互相覆盖？

「不会。两层保证：
- **JS 侧**：`define` 第一行就是 `if (modules.has(moduleId)) return;` —— **先到先得**，
  基础包先注册的不会被业务包覆盖。而且业务包是 `modulesOnly`，通篇不含 prelude
  （我 grep 过，连 `clear()` 都搜不到），**根本没有机会清空模块表**。
- **原生侧**：`loadScriptFromString` 只是往队列投递一次 `evaluateJavaScript`，
  **没有任何状态重置**，第二次求值就是往已有运行时里再灌一段脚本。」

### Q7：如果基础包里某个共享模块改了源码，但 mapping 没重新生成？

**这题往「我知道自己的坑」方向答**：

「会出问题 —— 而且是我目前**已知的边界**。mapping 现在是**按路径索引**的，不含内容哈希。
如果基础包侧某个共享模块源码变了、mapping 没重新生成，业务包里被剥掉的那份
会**静默使用基础包的旧实现**，不报错。

我计划补一个 `sourceHashes` 字段，不一致时告警 —— 这个还没实现。当前规避方式是
**基础包变更后重新生成 mapping 并重出业务包**。」

### Q8：为什么用 debug 变体？release 能跑吗？

「能跑，release 里 `useDeveloperSupport` 本来就是 false。我用 debug 是为了**快速迭代 +
能装就测**，核心是关掉 dev support 让 debug 也固定走 assets。代价是没有 RedBox / Dev Menu，
JS 报错只能看 logcat —— 我挂了个 `JSExceptionHandler` 把异常打到自己的 tag 上。」

## 4. 我能主动展开的深度话题（引导面试官往这问）

这些是你的**弹药库**。讲完主线后可以主动提一句「这块我读源码验证过几个点」，
把话题引到你准备充分的地方：

| 话题 | 你为什么能接住 |
| --- | --- |
| **为什么 `assets://` 前缀是 9 个字符** | `jniLoadScriptFromAssets` 会剥掉这个前缀；`setBundleAssetName` 内部就是拼 `"assets://" + name` |
| **APK 里 bundle 被 zip 压缩了会不会读不到** | 我一开始担心 `AAsset_getBuffer` 拿不到连续内存，实测**没问题** —— `AASSET_MODE_STREAMING` 会透明解压 |
| **旧架构 vs 新架构** | bridgeless 走 `ReactHost.loadBundle`，路径不同，我的 loader 写法**不适用** —— 这是明确边界 |
| **为什么业务包不能用 `.hbc`** | HBC 是二进制字节码，**无法拼接**；要走 HBC 得改成 RAM bundle / segment 机制 |
| **做什么能降低首次渲染耗时** | 懒加载业务包（当前是启动时预加载）；业务包的障碍是 `ReactActivity.onCreate → loadApp()` 会在业务包注册前就 `runApplication`，直接报「Application has not been registered」 |
